# Коротка документація BookingManagmentSystem

## Бізнес-завдання

Проєкт автоматизує підбір і бронювання залів: потрібно знайти приміщення потрібної місткості, перевірити його доступність і розрахувати ціну з урахуванням часу та додаткових послуг.

Для керування каталогом реалізовано створення, перегляд, редагування й видалення залів. Кожен зал має назву, місткість, погодинну ціну та набір доступних послуг. Зал із наявними бронюваннями видалити не можна.

Основний сценарій: пошук вільного залу → вибір послуг → створення бронювання → підтвердження з вартістю оренди, послуг і загальною сумою. Пошук не резервує зал, тому перед збереженням доступність перевіряється повторно.

## Правила бронювання та вартості

Пошук враховує мінімальну місткість і весь запитаний інтервал. Бронювання, яке закінчується о 14:00, не заважає наступному починатися о 14:00.

Час передається в ISO 8601 без `Z` або зміщення часового поясу, як місцевий час залу. Початок і завершення мають бути в межах одного дня, з 06:00 до 23:00. Тривалість — від 1 до 1020 цілих хвилин. Обрати можна лише послуги, доступні в конкретному залі.

| Час | Тариф оренди |
|---|---|
| 06:00–09:00 | Базова ціна −10% |
| 09:00–12:00 | Базова ціна |
| 12:00–14:00 | Базова ціна +15% |
| 14:00–18:00 | Базова ціна |
| 18:00–23:00 | Базова ціна −20% |

Якщо бронювання перетинає межі тарифів, кожен відрізок рахується окремо. Неповні години оплачуються пропорційно часу, а сума оренди округлюється до двох знаків після підсумовування. Кожна послуга оплачується один раз, без знижок чи націнок залу.

Наприклад, за базової ціни 100 бронювання з 10:00 до 14:00 коштує `2 × 100 + 2 × 115 = 430`. Послуги вартістю 25,50 і 10 збільшують підсумок до 465,50.

## API

Пошук:

```http
GET /api/halls/available?startTime=2030-09-01T10:00:00&endTime=2030-09-01T14:00:00&capacity=50
```

Створення бронювання:

```http
POST /api/bookings
Content-Type: application/json

{
  "hallId": 1,
  "startTime": "2030-09-01T10:00:00",
  "durationMinutes": 240,
  "serviceIds": []
}
```

Поточний API повертає `200 OK` із полями `id`, `hallId`, `startTime`, `endTime`, `hourlyRate`, `rentalCost`, `servicesCost`, `totalCost` і `selectedServices`. Для підключення послуг у `serviceIds` передаються їхні ID.

## Технічні рішення

Код розділено на чотири проєкти:

- **API** — контролери, HTTP-відповіді, Swagger і обробка помилок.
- **BLL** — сценарії роботи, перевірки часу, розрахунок тарифів і перетворення сутностей у DTO.
- **DAL** — репозиторії, EF Core, SQL Server, конфігурації таблиць і міграції.
- **Domain** — сутності, DTO, інтерфейси та винятки.

Сервіси й репозиторії підключаються через dependency injection. Контролери делегують роботу сервісам, а доступ до бази винесено в репозиторії.

`HallServices` пов’язує зали з доступними послугами. `Booking` зберігає інтервал, погодинну ціну й суми; `BookingServices` — вибрані послуги, їхні назви та ціни на момент бронювання. Зміна каталогу не змінює вже збережену вартість.

Створення бронювання виконується в транзакції. Репозиторій бере блокування залу через `UPDLOCK, HOLDLOCK`, повторно перевіряє перетин і зберігає запис. Запити, які використовують цей шлях, обробляють бронювання одного залу послідовно.

Унікальні індекси захищають назви залів і послуг від дублювання, зовнішні ключі — зв’язки між записами, а перевірки БД обмежують допустимі значення. Помилки обробляє спільний middleware: `400` — некоректні дані, `404` — відсутній ресурс, `409` — конфлікт. Serilog записує події в консоль і файли.
